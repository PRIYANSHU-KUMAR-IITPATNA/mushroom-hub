

# Mushroom Hub production implementation plan

> **Superseded stack plan:** This is the earlier Supabase implementation plan, retained as historical decision context. On 2026-11-04 the approved stack became Express + TypeScript + Zod + Prisma + Neon PostgreSQL, REST API `/api/v1`, with Google Cloud Run as the backend target and the existing Vercel frontend retained. Follow [backend architecture](./backend-architecture.md), [database schema overview](./database-schema-overview.md), and [backend local setup](./backend-local-setup.md) for current foundation guidance. No Supabase project, Neon connection, migration, or cloud deployment is implied.

**Status: superseded planning snapshot.** The current React/TypeScript/Vite application remains a local demo using simulated sessions and browser storage.

## Executive summary

The approved direction is Supabase (PostgreSQL and Supabase Auth), INR, admin-only financial/inventory administration, three application roles (`farmer`, `buyer`, `admin`), and a controlled pilot rather than an assumed full launch. The existing database specification already defines the core schema, foreign-key deletion behavior, RLS intent, trusted transaction requirements, inventory ledger, payment allocation/reversal accounting, effective-dated prices, and training capacity controls. Those are preserved here, not weakened.

Do not provision a hosted project containing user data until the chosen plan's project-creation flow confirms the intended Supabase region and the responsible owner has reviewed applicable residency constraints. Do not enable production authentication until the phone/OTP provider, abuse controls, session/recovery settings, and admin MFA have been approved and tested. Payment recording, real inventory/order transitions, and other user-facing operations remain disabled until their specific controls and pilot scope pass the gates below. The dated readiness closure in section 13 supersedes earlier unresolved/unverified statements where it gives a more current disposition.

The 90-day idempotency rule retains full request-hash/replay-result metadata for 90 days, then downgrades the existing scoped key row to a minimal non-reusable tombstone (empty request hash and no result). The actor/operation/key tuple remains unique and causes every late retry to conflict; it is not deleted by replay-metadata cleanup. This is separate from the retention of financial and business history, which remains append-only by default. Review the minimal tombstone under the approved privacy/retention process; never turn an expired retry into a new financial operation.

## 1. Baseline and non-negotiable guardrails

- Preserve the existing demo routes, data, and behavior. Do not repurpose or dual-write the existing `localStorage` keys or `sessionStorage` markers.
- Demo OTP code `123456`, simulated session markers, `mobileVerified`, locally saved roles/decisions, sample prices, and sample availability are not production identity or business evidence.
- Backend errors must remain visible; never fall back to demo storage after an authorization, network, or server failure. No production user data is written to browser storage as its source of truth.
- Keep development, staging, and production projects, Auth users, credentials, URLs, data, and deployments distinct. Use synthetic data in development/staging.
- Do not migrate demo data unless a separate, explicit consent, identity re-verification, mapping, and reconciliation process is approved. Default: no import.
- The only application roles are `farmer`, `buyer`, and `admin`. Business membership values such as `owner`/`member` are scoped membership metadata, not additional application roles.
- Admin-only operations remain harvest accept/reject; payment creation, allocation, reversal; inventory administration; training schedule/capacity administration; audit-log access; and other privileged workflow administration.
- Financial, inventory, history, audit, and ownership records are not cascade-deleted. Account closure archives/deactivates access. Anonymization is a separately approved, audited retention operation.
- No payment gateway, automated bank/UPI processing, buyer credit, or claim of provider-verified transfer is included in the pilot baseline.

## 6. Stage 2 — Database and security implementation design

**Prerequisites:** Stage 1 design and Stage 0 database/security decisions. The following is a migration dependency plan, not SQL to run.

### Ordered migration groups

1. **Foundation:** required PostgreSQL extensions; common timestamp/update support; stable profile identity and `user_profiles`; role grant history `user_roles`; append-only `audit_logs`; internal `request_idempotency`; append-only `private.admin_operator_actions` ledger; permanent non-API `private.admin_bootstrap_state` marker; narrowly scoped identity/role helper functions. Establish default-deny grants and RLS before any client exposure. Bootstrap is an operator-run transaction, not an installed client function.
2. **Profile and business ownership:** `farmer_profiles`, `buyer_profiles`, `buyer_businesses`, `buyer_business_members`. Add owner/member uniqueness and active-membership authorization. Decide approved member invitation rules before enabling them.
3. **Products, offers, and training schedule:** `products`, `catalogue_offers`, `training_sessions`; validate units, INR, effective time ranges and no overlapping active offer/rate periods. No production seed prices, stock or sessions without approval.
4. **Enquiries and training registrations:** `buyer_enquiries`, `enquiry_status_history`, `training_registrations`; constrain state and uniqueness; build trusted transition and capacity-locked registration functions.
5. **Orders and inventory:** `inventory_locations`, `inventory_balances`, `bag_orders`/lines/history and `buyer_orders`/lines/history; then `inventory_movements` and any cyclic source-line FKs after both order-line tables exist. Build ledger/projection invariant checks and transactional reservation, release, commit, receipt, spoilage, adjustment, and permitted reversal functions before presenting availability or fulfillment.
6. **Harvest decisions and rates:** `harvest_grade_rates`, `harvest_submissions`, `harvest_decision_history`; use effective-dated rates, two-decimal default precision, server-side half-up payable calculations, admin-only conditional decisions and immutable snapshots.
7. **Payments, allocations, and settings:** `farmer_payments`, `farmer_payment_allocations`, `admin_settings`; only after payment method/reference/date/reconciliation rules and reversal controls are approved. Add immutable payment/allocation/reversal audit and operation-key uniqueness. Buyer payment/credit tables remain out of scope.
8. **Final security and operational hardening:** enumerate every exposed table/view/function; review grants, RLS, constraints, indexes, foreign keys, trigger/function ownership, fixed `search_path`, logging, retention/expiry cleanup, and rollback/recovery limitations before UI integration.

### Enforcement boundary

- **Declarative constraints** enforce row-local validity: `NOT NULL`, `CHECK`, `UNIQUE`, FK, status/enum ranges, currency, positive quantities/amounts, field-shape consistency, and effective-time ordering. Add indexes for ownership/membership lookups, status/date access, ledger reconciliation, idempotency scope/expiry, and relevant foreign keys. Use a safe exclusion/transactional strategy for non-overlapping active rates/offers.
- **RLS** is enabled on every client-reachable table, default deny. It limits rows by active identity, active role, and explicit business membership, and exposes only approved reads. Use safe views/column grants for private fields. RLS alone cannot enforce protected-column allowlists or multi-record atomicity.
- **Grants and trusted functions** enforce protected columns and every privileged state change. Revoke direct client `INSERT`/`UPDATE`/`DELETE` on role grants, protected profiles, decisions, order lines/statuses, balances, inventory movements, payments/allocations, settings, histories, audits, and idempotency internals. Grant only required `SELECT` and narrowly scoped function execution. Do not expose destructive `DELETE` for retained history.
- Every trusted function derives the actor from verified `auth.uid()` (or a verified server-side principal), resolves the active application profile and role, checks ownership/membership and expected record state, validates inputs, and writes business rows plus histories/ledger/audit/idempotency atomically. Client-supplied user/business/actor IDs, role, status, amount totals, rate, or verification flags never grant authority.
- `SECURITY DEFINER` functions require fixed safe `search_path`, fully qualified objects, least-privilege ownership, strict argument validation, no unsafe dynamic SQL, explicit execute grants, and adversarial tests. Do not trust UI hiding, route selection, or caller-controlled JWT metadata for authorization.
- **Inventory:** lock order then all affected `(location_id, product_id)` balance rows in deterministic order; validate `available = on_hand - reserved`; commit order transition, movements, projection, history, and audit together. Admin acceptance reserves; cancellation releases once; fulfillment commits reservation and reduces physical stock. Locking/conditional transitions prevent concurrent oversell/double release/double commit. Reconcile sums of movement deltas against both projection values; report mismatch, never silently repair.
- **Payments:** admin only. Require configured method and reference for pilot records; evidence optional. Validate farmer, accepted harvest, INR, amount, scoped reference uniqueness and date; allocate only within accepted harvest outstanding and receipt remaining balance. Reversal creates new positive-magnitude receipt-reversal and matching allocation-reversal records with a non-empty reason; lock related rows and cap full/partial reversal at remaining reversible amounts. No update/delete of financial entries; all records/audit commit atomically.
- **Idempotency:** scope key by actor and operation; retain request hash and minimal replay result for exactly 90 days; same key/same payload returns the original result within the window, and same key/different payload rejects. At expiry, clear the hash and result but retain the actor/operation/key row as a tombstone; a post-expiry retry conflicts and never executes. Cleanup must be bounded, monitored, race-safe, retry-safe, and proven not to remove active replay protection. The tombstone contains no request/result payload and remains subject to privacy/retention review.
- **Foreign-key deletion behavior:** preserve the spec’s explicit actions. `auth_user_id -> auth.users` is `ON DELETE SET NULL`; stable ownership/business/financial/history references use `ON DELETE RESTRICT`; historical actor references use `ON DELETE SET NULL`. Request/history correlation FKs to idempotency rows use `ON DELETE SET NULL` only if a separately approved retention/anonymization process ever removes a tombstone; normal 90-day cleanup does not delete the row. The idempotency actor reference is `ON DELETE RESTRICT` while its tombstone exists. There are no cascades across financial/history facts. Close accounts by archive/deactivation; where removal is legally required, use a reviewed anonymization workflow that preserves stable referential integrity rather than deleting history.

**Rollback limitations:** version and review every migration; use expand/contract changes and forward corrective migrations. Schema rollback cannot reverse committed money, inventory, role, or audit history. Never delete committed records to simulate rollback. Restore only by approved recovery, into an isolated target first, then reconcile all committed events and obtain named authority before resuming.

**Verification evidence:** migration dependency graph and schema diff review; table/function/grant/RLS inventory; FK deletion-action check; static secret review; tests for every policy and function. Acceptance criteria are in Stage 4.

**Exit criteria:** Reviewed design preserves every audited invariant and resolves open ownership/retention choices required by selected migrations. No privileged write is reachable through untrusted direct client DML.

**Remain disabled:** Any client writes until policies/functions pass tests; payment entry until payment owner rules are approved; stock/order fulfillment until inventory concurrency and ledger reconciliation pass.

## 8. Stage 4 — Verification and migration rehearsal

**Prerequisites:** Stage 2 migrations/functions and Stage 3 integration available in isolated disposable/staging environments with synthetic accounts and records. No production test data.

**Required test suites and pass criteria**

1. **Unit/financial calculations:** Verify kg precision, rate/amount scale, numeric bounds, and standard half-up results at exact ties and immediately below/above ties. Verify accepted harvest value, net allocations, outstanding balance, partial/full reversal, unallocated remainder, and report totals all agree exactly using server-side numeric values. Pass: every expected value matches to paise; no floating-point drift; historical rate/value snapshots do not change after rate updates.
2. **Authorization/RLS/grants:** For anonymous, farmer A/B, buyer A/B, and admin identities, test cross-account SELECT/INSERT/UPDATE/DELETE attempts on every exposed resource; test forged IDs, role escalation, role revocation/re-grant, cross-business access, and direct access to protected functions/tables. Test protected identity fields (`id`, `auth_user_id`, `phone_verified_at`, `archived_at`), role/membership/ownership fields, admin status, harvest fields, and payment fields. Pass: only expressly allowed least-privilege operations succeed; all others deny without partial writes or data leakage.
3. **Trusted operation and rollback:** Inject a failure after each primary write but before history, ledger, allocation, audit, and idempotency completion for harvest decisions, role changes, profile update, order/inventory, payment/allocation/reversal, and training registration. Pass: transaction leaves no partial row, history, stock delta, financial amount, audit, or success-shaped idempotency result; same-key retry then succeeds exactly once.
4. **Inventory concurrency:** Run simultaneous acceptances that jointly exceed one balance; cancellation vs fulfillment; duplicate cancellation/fulfillment; and adjustment/spoilage versus reservation. Pass: no oversell, `0 <= reserved <= on_hand`, exactly one valid transition per order, one release/commit per accepted quantity, and ledger sums equal projection after every committed run. Deliberate projection mismatch must be detected and reported, not silently repaired.
5. **Training capacity concurrency:** Submit concurrent registrations at and above capacity and race registration against capacity reduction/session cancellation. Pass: non-cancelled registrations never exceed admin-configured capacity; duplicate active registration is rejected; outcome is atomic and understandable.
6. **Payment/reversal concurrency:** Race partial allocations and partial reversals; test farmer/currency mismatch, unaccepted harvest, duplicate reference, missing/invalid method/reference/date, evidence optionality, over-allocation, over-reversal, reversal of allocated and unallocated portions, required reason, and compensating correction. Pass: totals never exceed accepted harvest value or remaining receipt/allocation; each correction has immutable linked history/audit; failed operations roll back.
7. **Idempotency:** Replay identical keys/payloads within 90 days; reuse a key with altered payload; race same-key requests; replay after result expiry; run cleanup concurrently with retries; test old payment/reversal/inventory/order/role-operation keys after expiry and new keys for the same business fields. Pass: within-window duplicate returns original response; altered payload rejects; expired key never performs a new side effect; cleanup cannot delete live replay protection; new key is treated as new intent only if normal state/balance validation permits it.
8. **Migration/recovery rehearsal:** Apply migrations from empty schema and from supported prior version using synthetic data; rehearse forward corrective migration, frontend rollback, backup restore to an isolated target, and reconciliation. Pass: reproducible migration, no destructive financial rollback, documented measured restore result, reconciled counts/ledger/payment balances, and named approval before resume.
9. **Authentication/abuse:** Test OTP expiry/replay, send/verify throttles, abuse controls, provider delivery failure, cost alerts, session expiry/revocation, account closure, MFA enforcement and recovery. Pass: no fixed demo credential or untrusted client flag grants access; secrets/OTP values never appear in logs.
10. **Application release checks:** Type-check/build, end-to-end workflows, direct-route refresh, bilingual behavior, mobile layout, keyboard accessibility, error paths, and browser console/network review. Pass: no unhandled failures, secret exposure, unauthorized read/write, or silent storage fallback.

**Verification evidence:** CI output, test reports, concurrency/fault-injection logs, migration rehearsal record, region/provider evidence, access review, and restore/reconciliation timings. These are required evidence artifacts; this plan does not claim any have been produced or passed.

**Exit criteria:** All applicable tests pass; zero known cross-account or role bypass; rollback/fault-injection tests prove transaction atomicity; no unexplained accounting/inventory mismatch; restore and recovery procedures are measured and approved. Any failure keeps the affected workflow disabled.

**Remain disabled:** Every workflow whose tests or operational approvals are incomplete; all production writes until the controlled pilot go/no-go.

### 13.3 Idempotency lifecycle — 90 days

The approved retention remains exactly **90 days**. It applies to request/replay metadata, not to financial or business history.

1. Every retryable trusted command that creates or changes persistent business state must carry a client-generated UUID key scoped by the authenticated actor and fixed operation name. This includes profile/business-membership create/update/archive; role grant/revocation; catalogue/offer/settings/training-session changes; enquiry and status changes; bag/buyer order create/status/cancel; inventory receipt/reservation/release/fulfillment/adjustment/spoilage/reversal; harvest submission/decision/rate changes; training registration/status changes; account deactivation; and payment receipt/allocation/reversal. Reads and OTP delivery/verification calls do not use this business-command key; Auth abuse controls still apply to OTP calls.
2. While the request record is live, store only: actor ID, operation, key, a canonical semantic-request hash, creation/expiry timestamps, and a minimal non-sensitive result (entity type/ID and stable outcome needed to replay). Do not store OTPs, credentials, full request bodies, evidence, or unnecessary personal data. The server derives the actor; never trust a body actor ID.
3. Set `expires_at = created_at + 90 days`. Before expiry, the same scoped key and same canonical parameters returns the original committed result without executing again. Concurrent identical requests serialize so only one operation commits. The same scoped key with different parameters returns a conflict and performs no write. A different key is a new intent and must pass all current authorization, state, balance, stock, uniqueness, and business validation.
4. At or after expiry, return an explicit expired-key conflict; never execute that request as new and never return a success-shaped fallback. Clear `request_hash` (set it to an empty string because the audited column is `NOT NULL`) and set the result entity/result fields to `NULL`. Retain the actor/operation/UUID-key row and its expiry timestamp as a tombstone; a user must review current history and explicitly confirm a genuinely new action using a newly generated key.
5. The row's unique `(actor_user_id, operation, idempotency_key)` constraint is the durable non-reuse guard. The UUID key is not an authentication credential. Do not retain the original request hash or replay result after expiry, and do not delete the tombstone as part of 90-day cleanup. A late request therefore conflicts even though its replay metadata is gone. If a future lawful retention process removes tombstones, it must first establish an equivalent durable uniqueness guard and preserve referential integrity.
6. Cleanup must be race-safe with in-flight commands, retry-safe, bounded, monitored, and tested at the exact expiry boundary. A failed/partial cleanup must not enable key reuse. Yes: the financial operation history itself remains append-only and retained under the separate approved business/privacy retention policy after the 90-day replay metadata expires. Payment/allocation/reversal/history rows are not deleted by idempotency cleanup; correcting them uses reversals/compensating records.

No change to the approved 90-day period is proposed. The specification's nullable `expires_at` and history FKs to idempotency rows must be implemented consistently with the retained tombstone row. Full request/replay metadata expires at 90 days; the minimal actor/operation/key tuple remains only to prevent reuse and maintain historical references.

### 13.4 Pilot payment operating rules

- **Permitted methods:** manual admin-recorded bank transfer or UPI only. No cash, cheque, card, gateway, automated bank/UPI connection, buyer credit, or automated settlement claim is enabled without a separate approved design. Keep the method vocabulary explicit (recommended stable values `bank_transfer` and `upi`).
- **Receipt qualification:** record a receipt only after an admin has confirmed the transfer is credited/settled against the relevant bank/UPI statement or transaction record. A screenshot or user claim alone does not prove settlement. Store the actual transfer reference; method and reference are required. Evidence is optional.
- **Reference handling:** method and reference are required for every pilot payment. Reject a reference that is empty after trimming. Normalize whitespace consistently before storage/comparison, but preserve the originally supplied reference for audit whenever normalization changes it. Do not require an invented UTR/RRN/UPI regex. Detect duplicates by payment method + normalized reference + relevant source/payer account context. A suspected duplicate must not silently create a second record; present an explicit conflict for admin review/resolution and audit that resolution. The audited spec currently declares a globally unique nullable reference, which is not the same as this composite rule. Before payment migration, reconcile that constraint with the required duplicate key; for an initial single-source pilot, method + normalized reference uniqueness is the conservative baseline. If multiple source accounts are used, approve/configure a non-sensitive source-account identifier and include it in the composite check. Do not silently use amount/date/name as a dedupe key.
- **Date and amount:** store a precise transfer timestamp when available and preserve the `Asia/Kolkata` business date separately when needed for reconciliation/reporting. The audited schema currently has `payment_date` and `recorded_at` but no structured transfer-timestamp column. Before payment migration, decide whether a nullable transfer timestamp is needed and reconcile that addition with the spec; do not conflate UTC record-entry time with the transfer instant. Neither payment timestamp nor business date comes from browser-local time as authoritative evidence. INR positive amounts and settlement are two decimals.
- **Authority:** only an authenticated user with the active `admin` role and required MFA may record a receipt, allocate it, or reverse it, through trusted transactional functions. Farmers and buyers may read only their own allowed payment/allocation history. No new application roles are introduced.
- **Allocations and balances:** an admin may allocate all or part of a receipt to an accepted harvest, subject to both remaining receipt value and harvest outstanding. No automatic allocation. Any unallocated remainder stays unallocated, is not farmer credit, and does not reduce any harvest balance. Partial receipts and partial allocations are allowed. Outstanding is derived from accepted value less net allocations; never edited directly.
- **Reversals/mistakes:** no payment, allocation, or reversal is edited/deleted. Reverse a mistaken receipt with a new linked full/partial reversal and a required non-empty reason; reverse its allocated portion with matching allocation-reversal rows in the same transaction. Lock and validate remaining reversible amounts. Correct a wrong farmer/reference/amount by reasoned reversal and a new independently validated record. A mistaken allocation is corrected with an allocation reversal and, if appropriate, a new allocation. Every action is idempotent, atomic, and auditable.
- **Duplicates:** same-key retries return the original result within 90 days and are rejected after expiry as in section 13.3. An exact duplicate normalized reference is blocked; suspected duplicate transfers are held for statement review. Similar amounts/dates do not trigger silent deduplication. A genuinely separate transfer needs its own source reference and confirmed transaction.
- **Evidence:** optionally attach a redacted bank statement line, bank/UPI confirmation, or concise reconciliation note. Store only minimum metadata; strip unrelated account numbers, phone numbers, balances, and third-party personal data. If files are used, use a private access-controlled bucket with tested per-record authorization; no public links, credentials, full account secrets, or evidence in audit JSON/logs.
- **Reconciliation:** an admin is the reconciliation operator during the pilot; reconcile at least daily while pilot payment workflows are active. Before allocation, match the receipt to the source bank/UPI statement where available. Use a documented checklist for payment reference, amount, recipient/farmer, allocation, outstanding amount, duplicate detection, reversal status, optional supporting evidence, reconciliation actions, and exceptions. Store review outcomes and resolve exceptions through audited operations. A second-person review may be added operationally later; it is not a new database/application role. The owner must identify the named admin/person/team before real-user payment launch.

### 13.5 Financial precision and range

- Approved display/settlement policy is INR, exactly two decimal places (paise), standard half-up rounding. PostgreSQL `numeric` is exact; use it for rates, amounts, multiplication, allocation, reversal, balances, and aggregation. Never use binary floating point as the authoritative financial calculation.
- Keep weights at the audited spec's `numeric(12,3)` and rates/posted monetary rows at `numeric(14,2)`. A stored `numeric(14,2)` amount supports up to INR 999,999,999,999.99. Keep that monetary precision; do not widen it without a business requirement and explicit spec approval.
- The product of the full theoretical `numeric(12,3)` and `numeric(14,2)` ranges can exceed `numeric(14,2)`. Therefore exact stored monetary precision is suitable only when accepted operating values fit its declared range. Enforce a trusted server-side maximum/range check before storing the payable value; overflow/out-of-range requests fail visibly and atomically. Do not claim representability for every schema-permitted input.
- Multiply accepted weight by its snapshotted rate using exact PostgreSQL `numeric`; with the input scales, the exact product may have up to five fractional places. This is the necessary exact intermediate, not a change to settlement precision. Round once, half up, at the payable-value boundary to two decimals; store/report/allocate/reverse monetary values at two decimals. Preserve the exact rate and rounded value used by each historical transaction. Aggregate exact stored numeric rows and format reports to two decimals.
- Before harvest acceptance/payment features are enabled, approve the actual pilot weight/rate/value limits as operating values and prove boundary behavior in tests. This is a feature-level operating-value decision, not a blocker to unrelated schema/auth foundation work. No higher stored monetary precision is proposed.
- Implementation tests must cover exact half-paise ties and adjacent values, range boundaries, accepted value, partial/full allocations and reversals, outstanding, and aggregate reports. These are future tests, not claimed results.

## 15. Role lifecycle and administrator bootstrap alignment

This section records the approved operational design and supersedes earlier role/bootstrap wording where it conflicts. It does not represent SQL, a deployed privilege boundary, or tested controls. The current browser-local demo remains unchanged.

### Role lifecycle

- `user_roles.role` is exactly `farmer`, `buyer`, or `admin`. An active row has all three revocation fields null. A revoked row has `revoked_at` and a non-empty trimmed reason; its actor is populated for normal admin revocation and may be null only in a controlled operator/system action. Every grant requires a non-empty reason; `assigned_by` is the database-derived admin for ordinary grants and may be null only for a controlled operator action. These row rules are specified by CHECK constraints in the database specification.
- A partial unique index on `(user_id, role) WHERE revoked_at IS NULL` guarantees at most one active grant per role and profile, including concurrent insert attempts. Revocation conditionally updates an active row once; re-grant inserts a new `grant_id`; old grants and audit rows are retained and never reopened/deleted.
- Normal admins may grant/revoke farmer/buyer roles only for other users. They cannot change any admin grant or any of their own grants. Admin-role creation, revocation, or recovery is restricted to the operator process. Database constraints enforce role vocabulary, row shape, uniqueness and key/FK relationships; trusted transactions enforce actor authority, target eligibility, self-target denial, the admin-role prohibition, and atomic audit writes.
- `anon` and `authenticated` receive no direct SELECT/INSERT/UPDATE/DELETE on `user_roles`, `audit_logs`, operator-action, or bootstrap-marker tables, no internal-schema usage, and no execute privilege on bootstrap/operator recovery. `anon` receives no privileged-function execute. A narrowly scoped ordinary role grant/revoke function may be executable by the shared `authenticated` database role, but must derive `auth.uid()` and enforce active-admin, non-self, farmer/buyer-only authorization inside the function; RLS is default deny and safe reads use specific views/functions. Internal tables are not in exposed schemas. Privileged functions use least-privilege ownership, fully qualified object names, a fixed safe `search_path`, strict inputs, and no dynamic SQL. Retryable normal role grant/revocation commands use actor-and-operation-scoped `request_idempotency` and commit the idempotency row atomically with role and audit changes.

### One-time bootstrap and two-person evidence

- The initial bootstrap uses an internal `private.admin_bootstrap_state` singleton marker keyed by `bootstrap_name='initial_admin'`, with unique references to the stable profile, initial admin grant, and corresponding row in `private.admin_operator_actions`. The operator-action row has a unique change reference and approval-bundle digest, target Auth UUID/profile, operation code, and distinct primary/backup operator references. Its immutable insert-only treatment plus the marker primary key permanently prevents replaying bootstrap in that database, even after the first admin is revoked. The marker is not cleared during recovery. Auth UUID is an immutable snapshot, not an FK, so approved Auth identity deletion cannot erase the evidence.
- The primary and backup operator names and the initial administrator identity are deployment-time values. Both named operators must approve the same signed, canonical manifest bound to the environment/project, operation and target Auth UUID. A restricted runner verifies both independently authenticated signatures, distinct operators, exact target/environment and digest before connecting to the database. The database stores evidence references/digest and enforces distinct non-empty references and uniqueness of the recorded change reference/digest; it cannot prove human identity or signature validity by itself.
- In one operator transaction, verify the Auth identity through the selected provider-supported administrative workflow, confirm the Auth UUID exists and maps to no different profile, and confirm no marker or prior/historical admin grant exists. Create/map the stable profile, insert one operator-action record, create the first admin grant with a reason, write the `admin.initial_bootstrap` system audit event, and insert the permanent marker. Any error rolls everything back. No public RPC, browser function, reusable bootstrap function, client-supplied actor, or browser `service_role` credential is permitted.
- The migration identity requires reviewed schema/table/function/trigger/index creation privileges. The bootstrap transaction identity requires narrowly scoped internal-schema usage, read access to the needed Auth identity key/profile/role rows, and insert access to profile, role, operator-action, audit and marker rows. `anon` and `authenticated` are denied internal-schema usage, these direct writes, and operator execution. Exact Supabase role/connection permissions, Auth-row access, and exposed-schema behavior are **VERIFICATION REQUIRED** for the selected project and plan. Do not assume the `service_role` API key is a migration credential or an appropriate substitute.
- A wrong initial administrator is corrected by two-operator recovery: revoke the incorrect active admin grant and grant the verified intended identity a new admin grant; write operator-action and audit records atomically and retain the original marker/grants. Lost-admin recovery follows the same restricted two-person process. It does not rerun bootstrap, delete rows, rewrite history, or add an application role.

The database can enforce row CHECKs, foreign keys, unique/partial unique indexes, marker uniqueness, operator change/digest uniqueness, and client privilege denial when correctly configured. Transactional logic must enforce Auth/profile binding, no pre-existing admin, target eligibility, coupled role/audit/operator-action/marker writes, and recovery semantics. Distinct effective approvals must be verified by the restricted runner before it connects; a database CHECK can only validate recorded references, not prove signatures. Human approval, signing-key custody, operator authentication, identity verification, credential rotation, and protection against a privileged database owner bypassing controls are operational controls outside SQL.
